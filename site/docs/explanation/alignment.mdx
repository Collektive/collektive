# Alignment and Domain Partitioning

A device sends a single message per round, but a program usually contains many communicating operators.
How does the receiver know that a value comes from *the same* `share` call it is executing,
and not from another `share` somewhere else in the program?
The answer is **alignment**, the mechanism that matches messages to the operator that must consume them.
Collektive handles alignment automatically through a Kotlin compiler plugin;
this page explains what it does, why it matters for you, and the (few) cases in which you need to care.

## Paths and messages

During a round, every communicating operator (`neighboring`, `share`, `exchange`, and everything built on them)
is identified by its **path**: the sequence of calls, branches, and explicit alignment points
traversed from the program entry point to the operator.
The message a device sends is a map from paths to values (a serialized *value-tree*).

When an operator builds its `Field`, it looks up its own path in the messages received from the neighbors:

- neighbors that sent a value for that path are **aligned**, and appear in the `Field`;
- neighbors that did not (because they took a different branch, or did not run that part of the program)
  are **not aligned**, and are simply not part of the `Field`.

For example, consider the program `(if (con) { nbr(v1) } else { nbr(v2) }) + f(nbr(v3))`,
executed by three devices (MP₁, MP₂, MP₃): MP₁ and MP₂ evaluate the `else` branch, MP₃ the `then` branch.
In each device, only some paths of the program are evaluated (in green):

MP₁ and MP₂ are aligned on `nbr(v2)`, while MP₃ is the only one evaluating `nbr(v1)`, so its field there has no neighbors:

State works the same way: `evolve`, `share`, and `exchange` store their state under their path,
so each call site has its own independent memory.

## How Collektive computes paths

Collektive provides **strong**, **transparent**, **compile-time** alignment:

- **compile-time**: alignment tokens are generated by the compiler plugin while compiling your code;
  at runtime, devices only enter and leave the pre-computed scopes;
- **transparent**: you never have to annotate aggregate calls;
- **strong**: tokens encode the *semantic context* of the call (the function names and type arguments
  surrounding it), not just the position of the aggregate operators.
  Two structurally identical computations like `min(neighboring(x))` and `max(neighboring(x))` do not mix up their messages.

The compiler plugin visits each function that operates on an `Aggregate` and:

1. wraps every call to an aggregate function (any function with an `Aggregate` receiver or parameter) in an alignment scope,
   identified by the function signature plus a progressive counter for repeated calls in the same scope;
2. wraps every `if`/`when` branch whose body involves aggregate computations in a scope identified by the branch outcome;
3. descends into lambdas passed to aggregate functions, so that higher-order code is aligned according to the context in which the lambda is invoked;
4. **projects** the fields captured from outer scopes (see [below](#field-projection)).

For example, this function:

```kotlin
fun Aggregate<Int>.example(condition: Boolean): Int =
    if (condition) neighboring(1).all.values.max() else neighboring(2).all.values.min()
```

is compiled as if it were written (tokens simplified):

```kotlin
fun Aggregate<Int>.example(condition: Boolean): Int =
    if (condition) {
        alignedOn(true) { alignedOn("neighboring(Int)#1") { neighboring(1) }.all.values.max() }
    } else {
        alignedOn(false) { alignedOn("neighboring(Int)#2") { neighboring(2) }.all.values.min() }
    }
```

:::warning The compiler plugin is required
Without the plugin, all operators would share the same path and Collektive would fail at runtime with an
`AlignmentClashException`.
The Collektive Gradle plugin applies it automatically, see [Getting Started](../tutorials/getting-started.mdx).
:::

## Branches partition the network

In aggregate programming, `if` and `when` are not just control flow: they **partition the network**.
Devices evaluating different branches build different paths, hence they *cannot communicate* inside the branches.
Each branch is computed by an independent sub-collective, as if the other devices did not exist.

```kotlin
fun Aggregate<Int>.branching(): String =
    if (localId % 2 == 0) {
        "even sees ${neighboring(localId).neighbors.ids.set}"
    } else {
        "odd sees ${neighboring(localId).neighbors.ids.set}"
    }
```

On four fully connected devices, the result is:

```text
0 = even sees [2]
1 = odd sees [3]
2 = even sees [0]
3 = odd sees [1]
```

The same holds for the short-circuiting operators `&&`, `||`, and `?:`, whose right-hand side is evaluated only on some devices.

This is a feature: it lets you run different collective computations on different groups of devices
(drones and base stations, devices inside and outside an area, devices in different phases of a mission)
without any interference.
Together with `exchange`, branching is the only primitive needed to express all of aggregate programming.

### Field projection

What happens when a `Field` computed *outside* a branch is used *inside* it?
To respect the partitioning, the plugin **projects** the field, restricting it to the neighbors aligned in the branch:

```kotlin
fun Aggregate<Int>.captured(): String {
    val all = neighboring(localId) // computed outside: contains every neighbor
    return if (localId < 2) "low: ${all.neighbors.ids.set}" else "high: ${all.neighbors.ids.set}"
}
```

```text
0 = low: [1]
1 = low: [0]
2 = high: [3]
3 = high: [2]
```

The same projection is applied inside `alignedOn` blocks, and inside lambdas of aggregate operators.

### Pitfall: computing in the wrong branch

Projection has an important consequence: **neighbor-dependent computations must be done before branching**
whenever they must involve devices taking different branches.
The classic example is the gradient, in which the source takes a different branch than everybody else:

<DoDont>
<Dont label="inside the else branch the source is not aligned, so nobody ever sees it" result={<>On a line of five devices with source <code>0</code>: <code>{'{0=0.0, 1=∞, 2=∞, 3=∞, 4=∞}'}</code></>}>

```kotlin
share(Double.POSITIVE_INFINITY) { distances ->
    if (source) 0.0 else (distances + metric).neighbors.values.min()
}
```

</Dont>
<Do label="compute through the whole neighborhood, then select" result={<>Converges to <code>{'{0=0.0, 1=1.0, 2=2.0, 3=3.0, 4=4.0}'}</code></>}>

```kotlin
share(Double.POSITIVE_INFINITY) { distances ->
    val throughNeighbors = (distances + metric).neighbors.values.min()
    if (source) 0.0 else throughNeighbors
}
```

</Do>
</DoDont>

:::tip Rule of thumb
Use `if`/`when` when you *want* to separate sub-collectives.
When you just need to *select* a value (what field calculus calls `mux`), compute all the alternatives first and choose among the results.
:::

### Branches cannot return fields

Since fields are projected inside branches, a branch returning a `Field` would produce a field defined on a partial domain.
The plugin rejects it at compile time:

<DoDont>
<Dont label="compile-time error: this branch returns a Field">

```kotlin
val f = if (condition) neighboring(a) else neighboring(b)
```

</Dont>
<Do label="build the fields first, then choose entry by entry">

```kotlin
val fa = neighboring(a)
val fb = neighboring(b)
val f = fa.alignedMapValues(fb) { x, y -> if (condition) x else y }
```

</Do>
</DoDont>

## Loops and `alignedOn`

Calling an aggregate operator several times from the same position, as happens in a loop,
produces the same path at every iteration: the messages of different iterations would clash.
In this case, alignment must be made explicit with
[`alignedOn(pivot) { … }`](https://javadoc.io/doc/it.unibo.collektive/collektive-dsl/latest/collektive-dsl/it.unibo.collektive.aggregate.api/-aggregate/aligned-on.html),
which adds `pivot` to the path:

```kotlin
// one independent gradient per target, each aligned on the target's ID
fun Aggregate<Int>.distancesTo(targets: List<Int>): Map<Int, Double> =
    targets.associateWith { target ->
        alignedOn(target) {
            distanceTo(source = localId == target)
        }
    }
```

The pivot should be a value that identifies the iteration *consistently across devices*
(e.g., the ID of a target, the name of a resource) rather than a loop index whose meaning may differ from device to device.
Devices align with each other only on iterations with equal pivots,
so `alignedOn` can also be used as a dynamic form of domain partitioning.
This is exactly how the standard library implements [`multiGradientCast`](standard-library/spreading.mdx#many-sources-at-once).

With the default path representation, pivots must be hashable values:
`Boolean`, numbers, `Char`, `String`, `Uuid`, `null`, or pairs, triples, collections, and maps of them.
To align on your own data classes, align on one of their identifying properties.

The plugin [warns](compiler-plugin.mdx#aggregate-in-loop) when it detects an aggregate call inside a `for`/`while` loop without `alignedOn`.
Calls inside lambdas of collection operations (`map`, `forEach`, …) are not detected:
if you forget `alignedOn` there, Collektive fails at runtime with an `AlignmentClashException`.

:::caution
`alignedOn` blocks cannot return fields, for the same reason branches cannot.
Never call `align`/`dealign` directly: they are low-level primitives used by the plugin (and the compiler warns if you do).
:::

## Compiler diagnostics

Besides injecting alignment, the plugin checks the code for common misuses of the DSL,
such as aggregate calls in loops without `alignedOn` or branches returning fields,
and reports them as compiler warnings and errors.
See [The Compiler Plugin](compiler-plugin.mdx) for the list.

## Opting out: `@CollektiveIgnore`

Library authors may need to write code that must **not** be instrumented,
for instance, low-level utilities that manage alignment manually.
The `@CollektiveIgnore("reason")` annotation disables the plugin on a function, a class, or a whole file:

```kotlin
@file:CollektiveIgnore("Low-level utilities that manage alignment manually")

package my.library
```

You should almost never need it in application code.
