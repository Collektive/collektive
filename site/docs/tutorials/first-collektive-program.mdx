## Device counter

Let's write a program where *each device* learns the total number of devices in the network.
There is no central server: devices can only talk to their neighbors.

### Step 1: counting

We can use the [`countDevices`](https://javadoc.io/doc/it.unibo.collektive/collektive-stdlib/latest/collektive-stdlib/it.unibo.collektive.stdlib.accumulation/count-devices.html)
function from the standard library.
It builds a spanning tree rooted in a *sink* device, using the hop-count distance from the sink
([`hopDistanceTo`](https://javadoc.io/doc/it.unibo.collektive/collektive-stdlib/latest/collektive-stdlib/it.unibo.collektive.stdlib.spreading/hop-distance-to.html)),
and then sums `1` for every device along the tree, towards the sink
(a [converge-cast](../explanation/standard-library/collection.mdx)).

```kotlin file=<rootDir>/static/code/FirstCollektiveProgram.kt#L9-L15
```

:::note
This implementation has a limitation: only the sink knows the number of devices in the network.
Every other device knows the size of its own subtree.
:::

### Step 2: sharing the result

We now need to propagate the value accumulated by the sink to all the other devices.
We can broadcast it with the [`gradientCast`](https://javadoc.io/doc/it.unibo.collektive/collektive-stdlib/latest/collektive-stdlib/it.unibo.collektive.stdlib.spreading/gradient-cast.html)
function, which propagates a value from a source along the shortest paths
(a [gradient-cast](../explanation/standard-library/spreading.mdx)):


Now all the devices in the network know how many devices are currently connected.
This collect-then-broadcast composition is a recurring pattern in aggregate programming,
see [Composition patterns](../explanation/standard-library/overview.mdx#composition-patterns).

### Step 3: surviving failures

:::caution
What happens if the root fails, or the network gets split in two?
:::

The part of the network that still contains device `0` keeps counting correctly,
but the other parts have no sink anymore, and cannot compute anything meaningful.

We can fix this by *electing* the root instead of choosing it in advance.
A **leader election** algorithm, such as
[`boundedElection`](https://javadoc.io/doc/it.unibo.collektive/collektive-stdlib/latest/collektive-stdlib/it.unibo.collektive.stdlib.consensus/bounded-election.html),
selects a leader in every area of the network (here, areas of at most 25 hops), so every connected component gets its own root:

```kotlin file=<rootDir>/static/code/FirstCollektiveProgram.kt#L38-L57
```

:::tip[Success]
Now we're all set!
The final program counts the devices of each part of the network, and keeps doing so when the network is split or merged.
See [Gossip and Leader Election](../explanation/standard-library/gossip-and-leader-election.mdx#leader-election)
for how the election reacts when a leader fails.
:::
